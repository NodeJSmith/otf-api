## Objectives & Success Criteria

The `validator.py` module exists and can verify that anonymized output contains no leaked real PII values, preserves JSON structure, and parses through all Pydantic models. Unit tests confirm the validator catches intentionally leaked values and passes clean output.

## Subtasks

1. Create `src/otf_api/anonymize/validator.py`:
   - `ValidationResult` dataclass with: `passed: bool`, `leaks: list[LeakReport]`, `structural_errors: list[str]`, `model_parse_errors: list[str]`
   - `LeakReport` dataclass with: `file: str`, `field_path: str`, `real_value: str`, `category: str`
   - `PiiValidator` class:
     - `__init__(known_real_values: set[str])` — the set of all real PII values to scan for (collected from the original data during anonymization, or provided explicitly)
     - `validate_file(original: dict, anonymized: dict, filename: str) -> ValidationResult` — checks one file
     - `validate_batch(original_dir: Path, anonymized_dir: Path) -> ValidationResult` — checks all files in a batch
     - `_check_for_leaks(data: dict, filename: str) -> list[LeakReport]` — recursively scan all string values in the anonymized dict for matches against `known_real_values`. Also scan filenames.
     - `_check_structural_integrity(original: dict, anonymized: dict) -> list[str]` — verify same keys exist, same types, same nesting depth, nulls preserved
     - `_check_model_parsing(anonymized: dict, endpoint_path: str) -> list[str]` — attempt to parse the anonymized dict through the corresponding Pydantic model. Use the endpoint path (from `_meta.json`) to determine which model to use.
   - `collect_real_values(data: dict, mappings: list[FieldMapping]) -> set[str]` — walk a raw dict and extract all values from mapped PII fields into a set. Include URL-decoded variants (e.g., both `%40` and `@` forms of email). Include both the raw value and common variants (e.g., `"Jessica"` and `"jessica"`).
2. Create an endpoint-to-model mapping for the validator's model parsing check. This maps URL path patterns to the Pydantic model classes used to parse each endpoint's response. Use the existing client method → model relationships as the source of truth:
   - `/member/members/{uuid}` → `MemberDetail`
   - `/member/members/{uuid}/bookings` → list of `Booking`
   - `/v1/bookings/me` → list of `BookingV2`
   - `/v1/classes` → list of `OtfClass`
   - `/mobile/v1/studios/{uuid}` → `StudioDetail`
   - `/v1/performance-summaries` → list of `PerformanceSummary`
   - `/v1/performance--summary` (telemetry) → `Telemetry`
   - (etc. for all endpoints)
3. Update `src/otf_api/anonymize/__init__.py` — export `validate_anonymized` as a convenience function wrapping `PiiValidator`
4. Write `tests/test_anonymize/test_validator.py`:
   - `test_catches_leaked_name` — inject a real name into anonymized output, verify the validator flags it
   - `test_catches_leaked_email` — same for email
   - `test_catches_leaked_uuid` — same for UUID
   - `test_catches_leak_in_filename` — real UUID in filename is flagged
   - `test_passes_clean_output` — fully anonymized data with no real values passes
   - `test_structural_mismatch_missing_key` — removing a key from anonymized data is flagged
   - `test_structural_mismatch_type_change` — changing a string to int is flagged
   - `test_null_preservation_check` — non-null where original was null is flagged, and vice versa
   - `test_collect_real_values_includes_variants` — email collected in both `@` and `%40` forms
   - `test_case_insensitive_leak_detection` — "Jessica" detected even if anonymized output contains "jessica"

## Test Strategy

Tests in `tests/test_anonymize/test_validator.py`. Unit tests use small handcrafted dicts with intentionally planted leaks. The model parsing check tests use simplified fixture excerpts — just enough fields to construct a valid model instance. No network or file I/O.

## Review Guidance

- The leak scanner must check ALL string values recursively, not just mapped field paths — a real value could appear in an unmapped field
- Case-insensitive matching is critical — names and emails may appear in different cases
- URL-encoded variants must be checked (email `%40` form)
- The model parsing check must handle the different response wrapper formats (`data`, `items`, flat)
- Verify the endpoint-to-model mapping is complete for all 67 fixture files
